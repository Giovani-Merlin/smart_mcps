The orchestrator, in one page

A working reference for smart-mcps-orchestrate: how a plan becomes execution groups, how each group runs its coder/reviewer loop in an isolated worktree, and how the whole thing merges, escalates, and resumes. Synthesized from the source of truth — orchestrator/*.py and orchestrator/prompts/*.md — not paraphrased from older docs.

At a glance

The orchestrator takes an implementation plan, partitions its tasks into independent groups using codegraph-backed affinity signals, then runs each group as a headless claude -p coder session (plus a reviewer, for anything non-trivial) inside its own git worktree. Approved groups merge --no-ff into a per-run integration branch; the final merge to your main branch stays manual. Everything — including token spend — runs on your claude CLI subscription; the orchestrator process itself calls no LLM API directly.

01Overview

One document, one command, five stages. The plan never touches your working checkout — every group works in its own worktree, and the only two places state can land are a named grouping directory and a run directory, both under .orchestrator/.

Source: orchestrator/README.md, orchestrator/cli.py.

02Grouping & partitioning

group <plan.md> turns a plan into a DAG of independent execution groups: map each task to code regions, build an affinity graph over those regions, cluster it, then price and split against a token budget.

Task mapping: fixture register vs. mapper LLM

A plan can carry an embedded task map (files, symbols, depends_on, slices, route tags) that parse_task_map() reads deterministically — zero LLM calls, fully reproducible. Without one, group falls back to the mapper LLM (orchestrator/prompts/mapper.md), which reads the plan plus a codegraph file index and returns task→region mappings as JSON; every path and symbol it names is then verified against the real codebase, and misses are dropped with a flag rather than trusted.

PathLLM callsWhen it's used
Task map present0Plan has an embedded, parseable task map — the deterministic fast path; malformed input is a hard error, never a silent fallback.
No task map1 (mapper)orchestrator/prompts/mapper.md proposes task→region mappings; the orchestrator verifies every file/symbol against the codegraph index.

Affinity: what clusters together

Five signal types feed build_task_graph as weighted edges — how strongly two tasks pull toward the same group, not what runs before what:

SignalWeight (default)What it means
shared_file1.0Two tasks touch the same file (real or prospective).
call2.0A caller/callee relation between the tasks' symbols.
impact1.5One codegraph impact -d 2 overlap between tasks.
prose_neighbor0.5Not a codegraph signal — the only edge a region-less task gets, toward its plan-order neighbor.
semantic1.5A matched implements/consumes route tag; the whole semantic layer is rescaled by clamp(Σw_structural / Σw_semantic, floor, ceil) so it dominates only when the structural graph is near-empty (greenfield).
Known limitation

call and impact feed both affinity and precedence. On a mature, densely-connected codebase the precedence half can saturate into one cycle — every node becomes a "hub." Zeroing these weights removes the affinity signal too; it is not a workaround for the cycle problem.

Clustering shape

Louvain community detection (seed 42, stable run to run) does the clustering; hub_threshold (a fraction of all tasks, not a count) reclassifies high-degree nodes into hub roles with real scheduling consequences — a utility_hub is isolated into its own group and scheduled first, every aggregator_hub is pooled into one trailing group.

The granularity dial (--granularity / [partition] granularity) controls how eagerly small groups get folded together — three levels, each relaxing one more guard than the last; the budget cap, slice must-link, and cycle checks are hard at every level:

LevelRelaxesEffect
independent (default)nothingEnforces both chain_compatible and the makespan no-regression check — today's behaviour, byte-for-byte.
balancedchain_compatibleStill rejects a merge that would regress the simulated zero-communication makespan.
monolithic+ makespan checkCollapses as much as the hard guards allow.

Pricing and the budget cap

Each group's estimated token cost is summed from source bytes, an existing-file tool allowance, and prospective-file size_hints; the partitioner enforces a cap derived from the compiled base context size plus headroom:

work = source_bytes / bytes_per_token * slack_multiplier
     + len(existing_files) * per_file_tool_allowance
     + Σ prospective files: size_hints[f] ? size_hint_<class> : per_file_tool_allowance

head = (base_tokens + spec_tokens_allowance) * slack_multiplier
cap  = max(token_budget - head, 0)

docs/orchestrator-grouping-config.md · orchestrator/grouping/estimator.py

A declared slice (a must-stay-together set of tasks) whose own summed work exceeds the cap is a hard GrouperError by default, naming the slice, every member, and the overshoot — override with --allow-oversized-slice to keep it whole as one flagged group.

Which groups get a reviewer

A difficulty score in [0, 1) — a weighted sum of five saturating-normalized signals (files touched, max fan, hub touches, cross-group edges, verification items) — picks each group's review intensity at grouping time:

ThresholdDefaultBelow it
d_review0.35self_verify — no reviewer session at all
d_hard0.65below: paired (one reviewer); at/above: paired_plus (mandatory extra verification pass)

run --review-intensity <tier> overrides the computed tier for every group in the run — a blunt instrument for "review everything" or "trust everything."

The index fingerprint: content hash, not operational counters

index_fingerprint() (orchestrator/grouping/graphing.py) is a sha256 over a canonical logical export — sorted symbol ids, sorted file paths, sorted edges, canonically serialised — not over codegraph status -j's operational counters (queue depth, uptime, cache size), which used to churn the fingerprint even when the index's actual content hadn't changed. Before partitioning, await_index_quiescence() polls the fingerprint until it reads identical across several consecutive reads; a fingerprint that keeps changing fails the grouping loudly, naming every distinct value observed, rather than partitioning against a moving index.

Index-stable, not reproducible

Pinning the index makes a partition index-stable — the deterministic core (Louvain seed 42, sorted iteration) reproduces byte-identically given the same content — but the mapper that turns tasks into files/symbols is an LLM call with no temperature or seed control, so a task→region mapping can still differ against a byte-identical index. Do not read "index-stable" as "reproducible": the mapper's output is the one remaining source of run-to-run drift, and it is not content-addressed today.

The recorded ProvenanceEntry (grouping trace) carries the fingerprint alongside the Louvain seed and resolution used, so a partition's exact key is reconstructable after the fact. On resume/reuse, the recorded fingerprint is compared against the current index; a mismatch is a hard failure naming both fingerprints unless --allow-index-drift downgrades it to a loud warning and forces a re-partition. A fresh group invocation never fails on mismatch — only reuse of a stale partition does.

03The shared base context

Every worker session in a run — the base session itself, and every coder/reviewer forked from it — shares one compiled document so the same repo conventions and architecture summary don't have to be re-derived per group.

compile_base_context() concatenates four sections into base-context.md, written once at group time and snapshotted again into the run directory at run time:

  1. Worker ground rules (orchestrator/prompts/worker_ground_rules.md, plan U15) — worktree confinement, commit-early-and-often, the permission-denial retry protocol, and the report-block rules for both coder and reviewer, written to refer forward ("the spec you will be given below", "the plan document that follows it").
  2. Repo conventions — the full text of CLAUDE.md and AGENTS.md, if present.
  3. Codebase architecture — a codegraph summary of the repo.
  4. The plan document — the plan's own text, with its embedded task-map block stripped (that block is grouper input, not worker context).

Ground rules come first specifically so every forked worker reads its behavioural invariants once, from the cached prefix, before the plan-specific and repo-specific material that follows — paid once per run instead of resent per fork. The per-fork coder/reviewer prompt (§06) then keeps only a compact tail restatement of the report contract's exact tag and permitted status values, not the full prose.

Compilation is byte-stable: identical repo state + plan + codegraph summary always produce identical bytes, because the document feeds a prompt-cache-sensitive session head — the run command forks every coder and reviewer session from one shared base session rather than re-sending this context per group.

compile_base_context() orchestrator/grouping/base_context.py 
def compile_base_context(repo_root: Path, plan_path: Path, codegraph_summary: str) -> str:
    """Worker ground rules + repo conventions + codegraph architecture summary +
    the plan document.

    The ground rules come first (plan U15) so every forked worker session reads
    its behavioural invariants once, from the cached prefix, before the
    plan-specific and repo-specific material that follows. The task-map block is
    grouper parser input, not worker context (R27): it is stripped from the plan
    text before embedding, never from the plan file itself.
    """
    sections = ["# Base context\n", load_template("worker_ground_rules").strip() + "\n"]

    for name in CONVENTION_FILES:  # ("CLAUDE.md", "AGENTS.md")
        path = repo_root / name
        if path.is_file():
            sections.append(f"## Repo conventions ({name})\n\n{path.read_text().strip()}\n")

    if codegraph_summary.strip():
        sections.append(f"## Codebase architecture (codegraph)\n\n{codegraph_summary.strip()}\n")

    plan_text = strip_task_map(plan_path.read_text())
    sections.append(f"## Plan document ({plan_path.name})\n\n{plan_text.strip()}\n")
    return "\n".join(sections)

04Group lifecycle

Ten states, scheduler-owned (orchestrator/execution/scheduler.py:79-97). Three are terminal in the ordinary sense; a fourth — INTERRUPTED — is deliberately not, because it means the harness died, not the work.

StateMeaningClass
PENDINGNot yet admissible — waiting on the scheduler's first pass.queued
READYAdmissible now: DAG deps met, no hold against it.queued
RUNNINGCoder session active in its worktree.active
REVIEWINGReviewer session judging the latest round (skipped entirely for self_verify).active
REWRITINGSpec being rewritten from surprises/operator guidance before the next generation.active
MERGINGIntegrationMerger attempting the --no-ff merge.active
COMPLETEDMerged cleanly; dependents release.terminal
FAILEDRewrite cap or generation cap exhausted with no operator grant. Terminal — edit state.json back to ready to retry after fixing the cause.terminal
RESOLVEDA FAILED group's stranded work landed on the integration branch via the resolve routine — distinct from COMPLETED because it never claimed a review verdict, distinct from plain FAILED because the work wasn't lost. Releases dependents the same as COMPLETED.terminal
INTERRUPTEDEnvelope failure — the claude process or API died under the group, not the work. Non-terminal: a plain resume re-enters it.non-terminal

Why file overlap holds a group back

Above concurrency = 1, two groups declaring a file in common are never both running — a scheduler invariant, not a config option. status names the hold explicitly: held (file_overlap) by g1 on cli.py. Serial (concurrency = 1) is the default precisely because each group's worktree is cut from the integration tip at its ready→running transition, so one-at-a-time stacks work with zero cross-group conflicts.

A separate failure gate (HoldReason.FAILURE_GATE) holds any group sharing a declared file with a FAILED-but-unresolved or INTERRUPTED group — an overlapping successor must never build on a hole a failed group might have left.

05Coder / reviewer review loop

The orchestrator ferries control, not content: round triggers carry statuses and artifact pointers; the reviewer computes its own diff from the shared git worktree rather than being handed one.

The circuit breaker

A coder session is retired and respawned as a fresh generation when either bound trips — reset against the latest round's context usage, never the sum of all turns (summing once inflated the signal ~50× and retired healthy coders):

FieldDefaultTrips when…
context_token_limit200,000the coder's last-round context occupancy exceeds it
max_rounds_per_generation3the current generation runs this many review rounds
max_generations3respawns exhausted — the group fails to the operator (escalated as CAPS_EXHAUSTED first)

On retirement, a condensed handoff prompt (handoff.md) carries the retirement reason, outstanding required changes, and a diff summary into the next generation's fresh fork.

Merge-conflict resolve-in-place, before rewrite

Since plan U1, a merge conflict no longer jumps straight to a full spec rewrite. The group's own coder session — still holding full context of the work it just built — gets up to max_conflict_resolve_attempts (default 1) warm-resume attempts to fetch, merge/rebase the integration branch, hand-resolve, and commit, using conflict_resolve.md. Only if that attempt doesn't report completed, or attempts are exhausted, does the loop escalate MERGE_CONFLICT and fall back to _rewrite().

Rewrite cap

max_rewrites (default 2) bounds how many times one group's spec can be rewritten in response to a surprise, a stuck coder, a hard reviewer verdict, or a merge conflict, before the group fails outright — escalated as CAPS_EXHAUSTED first; an operator answer grants one more guided rewrite instead of failing.

Not every surprise counts against that cap. Surprise.kind == "informational" (plan U13) is a broadcast fact — a changed test baseline, a pre-existing red suite — that gets folded into the next generation's briefing without incrementing rewrites and without triggering a speccer call. Only a surprise of any other kind actually calls _rewrite(); a group that consumed sixteen informational surprises still has its full rewrite budget for a genuine merge conflict or a genuine hard reviewer verdict.

Re-entry after a crash

On resume, the executor looks for a live coder session entry (no retirement_reason) at the group's persisted generation in the manifest and warm-resumes it with reentry.md — re-orienting from git status/git log rather than restarting. If the persisted context already exceeds the breaker limit, or the warm resume itself fails, it falls back to a fresh fork from base instead.

07Escalation / human-in-the-loop

Headless claude -p workers cannot pause mid-turn to ask a question. The only channel is report-then-resume: a coder ends its turn with a status the orchestrator recognizes as stuck, the review loop escalates and blocks that group's coroutine — sibling groups keep running — and resumes it once you answer.

On by default

HITL is enabled at intensity on_stuck out of the box. An unattended run needs --intensity autonomous (or [escalation] intensity = "autonomous") explicitly — otherwise a run can block indefinitely on an unanswered escalation, since timeout_s defaults to blocking forever.

The ten escalation kinds

EscalationKind (orchestrator/model.py:171-188): six are decision points that would otherwise auto-resolve; three (GROUP_START, RESPAWN, MERGE_APPROVE) are approval gates only the interactive tier raises.

coder_questionCoder emitted needs_input + a question.on_stuck
coder_blockedCoder reported blocked/failed.on_stuck
reviewer_too_hardReviewer verdict too_hard.on_stuck
reviewer_structuralReviewer verdict structural — the group boundaries themselves are wrong.on_stuck

Escalation source

--escalation-source workers_via_orchestrator (default) surfaces a coder's needs_input question to you as-is. orchestrator_only downgrades it: EscalationPolicy.should_escalate() refuses coder_question outright when the source is orchestrator_only, and the review loop routes the same moment through coder_blocked instead — no direct worker→human channel, just the existing blocked/rewrite path.

The request/response file protocol

Deliberately boring: EscalationBroker.raise_escalation() writes escalations/request-<id>.json, logs a loud line to run.log, then polls (poll_interval_s, default 1.0s) for a matching response-<id>.json — from a worker thread via asyncio.to_thread, so the event loop and sibling groups are never blocked. smart-mcps-orchestrate answer <run_id> <esc_id> --action answer|skip|abort writes that response file; the blocked group's coroutine picks it up by correlation id.

Unanswered, no timeout set

Blocks indefinitely — a live operator is expected. This is the default (timeout_s = null).

Unanswered, timeout set

Falls back per on_timeout: autonomous (default), skip, or abort.

Proposed, not implemented — ADR-0005

docs/adr/0005-hitl-permission-routing-transport.md is a design proposal only; it changes no code today. It answers one question — how would a live PreToolUse permission gate (blocking a dangerous tool call before it runs, mid-turn) talk to the same escalation channel described above? — for a future implementation plan. The recommended transport reuses escalations_dir itself: the hook writes its own request file and polls for a response, and the broker gains a lightweight watcher for new request files. None of this exists in the codebase yet — there is no PERMISSION_REQUEST escalation kind, no hook script, and no broker-side watcher.

08Tool & permission gating

What actually constrains a worker session today — reported plainly, not aspirationally.

Every worker session is shelled by SessionRunner._call() (orchestrator/execution/sessions.py), which passes exactly two gating flags straight through to the claude CLI:

Config fieldDefaultCLI flag it becomes
[execution] permission_modeacceptEdits--permission-mode acceptEdits
[session] allowed_tools[]--allowedTools a,b,c (only sent if non-empty)
acceptEdits covers edits, not Bash

Orchestrated coders cannot run pytest or git commit unless an approver is wired up separately — a large hidden cost driver, since a coder that cannot verify its own work burns rounds guessing instead.

There is no fine-grained per-tool allowlist/denylist system built into the orchestrator beyond these two flags. The only in-band defense against a dangerous or repeatedly-denied command is prompt-level, in coder.md: retry the identical denied command up to three times, then stop and report permission_denied with the exact command in denied_command. That report routes the group to INTERRUPTED (not FAILED) — the harness reported a real-world block, the coder's work isn't wrong, and a plain resume re-enters the same worktree once the denial is cleared:

class PermissionDenied(Exception):
    """A coder reported ``permission_denied`` (plan U3): the harness is healthy,
    but a sandboxed command was refused after the coder's identical-retry budget.
    Routes the group to INTERRUPTED, never FAILED — the work is unfinished, not
    wrong, and a plain ``resume`` re-enters the same worktree. [...]"""

orchestrator/model.py:233-242

The live, mid-turn PreToolUse gate described in ADR-0005 (§7 above) — which could actually block a specific dangerous tool call before it executes, rather than relying on the coder to self-report after the fact — is proposed, not built.

09Merge strategy

IntegrationMerger (orchestrator/execution/merge.py) owns one branch per run: orchestrator/run-<run_id>, created from the launch ref and checked out in its own worktree so the operator's own checkout is never disturbed.

Integration branch
orchestrator/run-<run_id>
Group branch
orchestrator/<run_id>-<gid>
Merge mode

Final merge to main

Empty-merge refusal

Before merging, commits_ahead() counts commits on the group's branch not yet reachable from the integration branch — read before the merge, since a clean merge makes that same count read zero afterward, which would make a real merge indistinguishable from a no-op. A count of 0 refuses outright:

if ahead == 0:
    raise MergeError(
        f"group {group.id} branch {branch} has no commits ahead of "
        f"{self.branch} — refusing to merge nothing"
    )

orchestrator/execution/merge.py:80-85

Conflict handling

A conflicted git merge --no-ff is aborted cleanly (git merge --abort) — the integration branch is left exactly where it was — and raises MergeConflict, naming the conflicted files, the incoming group, and every already-merged group whose declared files collide. The review loop turns that into a Surprise (kind: "merge_conflict") fanned out to every named group, then tries the resolve-in-place step (§05) before falling back to a full spec rewrite.

Worktree cleanup

A clean merge removes the group's worktree. A merge that fails leaves the worktree in place, uncommitted leftovers and all, for inspection — cleanup is never forced on a dirty tree.

Provisioning: group and integration worktrees alike

Every group worktree is provisioned with the run's provision_args (typically uv sync --all-extras) right after creation. IntegrationMerger.ensure() provisions the integration worktree the same way, once, the first time it is created — it is the tree that represents the run's actual output, so an operator going there to run what was just built finds a working environment rather than a bare checkout. Each worktree's provisioning is logged with the exact command used.

10Preflight failure classification, the baseline, and auth recovery

Two mechanisms that stop a run from spending its whole rewrite/generation budget on causes no coder can fix: a preflight failure is typed before anyone is blamed for it, and an expired credential tries to heal itself before it pages an operator.

Preflight failure kinds

run_preflight (orchestrator/execution/preflight.py) classifies every failure into a PreflightFailureKind before raising PreflightFailure, instead of handing the merge gate a bare exit code:

KindWhenWhat it meansWhere it routes
envExit codes 2/3/4/5, or exit 1 whose output shows a collection-phase error (ImportError while loading conftest.py, ModuleNotFoundError, a bare ImportError).Zero tests ran — not evidence about the diff.Fails the group fast with the diagnosis attached; does not call _rewrite and does not advance the generation counter.
timeoutThe check command hangs past check_timeout_s (default 900s).A hung check command, not a diff problem.Same fast-fail path as env — no rewrite spent chasing a hang.
regressionExit 1 with tests that actually ran and actually failed, and the failing set is not entirely pre-existing per the baseline (below).A real regression attributable to this diff.Keeps today's rewrite-and-respawn behaviour — escalated as preflight_failed (EscalationKind.PREFLIGHT_FAILED), distinguishable from a git merge_conflict escalation.

The check command itself gains -p no:cacheprovider and a --junitxml=<path outside the worktree> when pytest is detected, so the clean-tree requirement holds after the run, not just before it — no .pytest_cache or JUnit XML ever lands inside the worktree.

The launch-branch baseline

At run start, the check command runs once on the launch branch and its per-test outcome set is persisted to the run directory as preflight-baseline.json (test ids, outcomes, exit code, command, commit sha). Every subsequent preflight failure's failing-test set is compared against it:

VerdictMeaning
new_failuresAt least one failing test on the group's head was not failing on the baseline — attributable, keeps the rewrite path.
pre_existingEvery failing test on head was already failing on the baseline — explicit "not attributable," routed the same as an env failure rather than spending a rewrite.
no_baselineNo baseline could be captured (e.g. the launch branch itself doesn't run cleanly) — degrades to "cannot attribute," never to a false attribution.

Beyond the deterministic ladder above, when a failure still needs judgement, the classification is performed by the orchestrator's own session — not a separate cheap model — because it already holds the plan, the codegraph summary, and the group's spec, and its written diagnosis is what the next generation is told, together with the check output's short test summary info tail (not just a path to preflight-check.log).

The auth-refresh ladder

A 401 … re-authenticate used to be a bare SessionError that, under on_group_failure=halt, set RUN_HALTED for every group in the run. orchestrator/execution/auth.py replaces that with three rungs, each cheaper than the next, implemented as AuthLadder.recover() for (a)/(b) and the existing UsageLimitGate machinery (constructed with probe=ladder.recover) for (c):

RungWhat happens
(a) Local expiry checkAfter any long pause, and before the first retry, read expiresAt from ~/.claude/.credentials.json — no network call, both fields are epoch milliseconds.
(b) Orchestrator-side refreshIf stale, the unconfined orchestrator process (confinement is per-worker-session; see §08) triggers a refresh itself and re-reads the file to confirm expiresAt advanced.
(c) Pause-and-notify, self-releasingIf refreshTokenExpiresAt has also passed, or the refresh doesn't advance expiresAt, or a live call still 401s: arm a pause and notify, re-probing periodically via the same "arm, poll, self-release" gate usage limits already use, clearing itself once recover() reports healthy again.

The two incidents that motivated this were a refreshed token that could not be written — already fixed separately, since confinement.py:428 grants ~/.claude/.credentials.json a single-file read-write rule — not a login that had actually lapsed. That is why rung (b) tries to self-heal before rung (c) ever asks an operator for something they mostly cannot supply.
