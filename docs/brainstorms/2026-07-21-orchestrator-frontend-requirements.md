# Orchestrator Observatory (Front-End) — Requirements

## Summary

A local front-end — the **Observatory** — that makes an orchestration run legible while
it runs and after it finishes, so you can verify what is happening, debug and improve the
orchestrator, and do it across different projects from one interface. It is a thin Python
web server (Starlette/FastAPI + uvicorn) that watches a run's on-disk artifacts under
`<repo>/.orchestrator/runs/<run_id>/`, serves them to a React/Vite single-page app over
REST + SSE, and exposes one narrow write path: answering human-in-the-loop (HITL)
escalations. It does not launch, resume, or abort runs in v1. The orchestrator core is not
modified; the Observatory is strictly out-of-process, reading files and writing escalation
responses through the orchestrator's existing `answer` code path.

## Problem Frame

The orchestrator already communicates through exactly one channel: the filesystem. A run's
state (`state.json`), session join (`manifest.json`), event log (`logs/run.log`), task DAG
(`groups.json`), and HITL channel (`escalations/request-*.json` / `response-*.json`) are
all flat, well-structured files with stable conventions (documented in
`orchestrator/README.md`). Human input flows back as `escalations/response-<id>.json`,
writable directly or via `smart-mcps-orchestrate answer`. There is **no HTTP/websocket/
streaming surface** today; the de-facto protocol is files + polling.

That is fine for a supervising process but opaque for a human. The current way to "watch"
a run is to `tail logs/run.log` and `ls escalations/` in a terminal, and answer by hand-
crafting a CLI command with correlation ids. The live smoke run never even exercised the
HITL loop end-to-end — no escalation ever fired against real CLI subagents — so the
two-way communication path the orchestrator was built around is still unverified in
practice. And there is no way to see *why* a specific agent got stuck without opening its
raw Claude transcript `.jsonl` by hand.

The gap is not the orchestrator's communication model; it is the absence of a human-facing
surface over it. A browser cannot read the filesystem, so the real design question is what
bridges the run files to a UI — and how to send answers back — without perturbing the
system under test.

Prior art in this repo: a React + Vite + TypeScript prototype (`ui/`) already exists on
branch `orchestrator/run-smoke1` — but it was *generated by the orchestrator itself* during
a smoke run. It is a static display shell (`GroupBoard`, `EventLog`) driven entirely by
hardcoded fixtures in `ui/src/sample-run.ts`, with no data layer, no backend, and no run
selector. Its `types.ts` hand-mirrors `orchestrator/execution/scheduler.py` and
`orchestrator/model.py`. It is a useful starting skeleton, not a working tool.

## Key Decisions

- **Scope is observe + answer, not control.** V1 reads run state and resolves HITL
  escalations (answer / skip / abort). Launching, resuming, aborting runs and managing
  groups from the UI are explicitly deferred (see Non-Goals). Rationale: the smallest
  surface that still exercises the two-way communication the user is worried about, and it
  keeps the backend a reader plus a narrow write path rather than a subprocess supervisor.

- **Bridge = thin local Python backend + SPA over REST/SSE.** Chosen over a desktop app
  (Tauri/Electron direct-fs — heavy new toolchain, wrong stack for the existing web
  prototype) and over a static snapshot poller (no live push, cannot write answers).
  Starlette/uvicorn are already pulled in transitively via `fastmcp`, so the added
  dependency surface is small. The backend watches the run dir and pushes; the SPA reuses
  the `ui/` prototype. Launchable as a new `smart-mcps-orchestrate ui` subcommand.

- **Orchestrator core stays untouched; write path reuses the existing `answer` logic.**
  The Observatory imports and calls the same function that backs the `answer` subcommand
  (which validates the escalation exists and the action is legal, and writes
  `response-<id>.json`) rather than duplicating validation or shelling out. Rationale:
  single source of truth for the HITL contract, and an observatory that never perturbs the
  process it is meant to help debug.

- **Live depth = first-class artifacts (live) + per-agent transcript drill-in (polled).**
  The board (state.json), event log (run.log via SSE), DAG (groups.json), pending
  escalations, and each group's finished report/verdict JSON are surfaced directly.
  Clicking a group opens a drill-in that fetches and parses that agent's
  `~/.claude/projects/**/<session_id>.jsonl` transcript (path from `manifest.json`) and
  re-polls every few seconds while open. Rejected: adding `stream-json` streaming to the
  orchestrator (modifies the system under test, scope creep) and true per-transcript SSE
  tailing (a watcher/stream per open pane for marginal gain over a short poll).

- **Multi-project via a Project Registry file.** A single frontmatter-style YAML lists
  target repos by `name` + `repo` path (reusing the repo's established date/topic/plan/
  branch vocabulary). The UI shows a project switcher; for the selected project it scans
  `<repo>/.orchestrator/runs/` for runs. Chosen over one-repo-per-launch (not unified) and
  auto-discovery under a root (noisy, slow on large trees). This is the "unified
  front-matter" from the original request.

- **Transcript parsing is tolerant.** The `.jsonl` transcript is Claude Code's own format
  and may drift; the parser skips unknown event types and degrades gracefully rather than
  breaking the drill-in.

- **Reads rely on the orchestrator's atomic writes.** `state.json` is written
  write-then-rename, so a reader never sees a torn file; the Observatory relies on this
  invariant rather than adding its own locking.

- **Local-only, no auth in v1.** The server binds to `127.0.0.1` and ships no
  authentication. It reads local files (including transcripts) and can answer escalations,
  so it is a single-user local dev tool, not a hosted service.

- **Branch: merge, don't re-cut.** Build on the existing `test/orchestrator-frontend`
  branch (the `smart_mcps-fe-test` worktree), first merging `feat/multiagent-orchestrator`
  into it to gain the HITL commits (U11–U14) it currently lacks, then bringing in the `ui/`
  prototype. This directly answers "can we run the orchestrator from this branch to test
  it": **yes, but only after that merge** — today the branch is 3 commits short of the
  escalation flow the Observatory exists to exercise.

## Requirements

### Backend (server)

- R1. Provide a `smart-mcps-orchestrate ui` subcommand that starts the Observatory server
  bound to `127.0.0.1` on a configurable port, serving the SPA and the API below.
- R2. Load a **Project Registry** file (frontmatter-style YAML: list of `{name, repo}`).
  Expose an endpoint listing registered projects. Registry path is configurable; default
  location decided at plan time.
- R3. For a selected project, enumerate runs by scanning `<repo>/.orchestrator/runs/`, and
  expose a per-run **snapshot** endpoint composing `state.json` (group states, generations,
  live PIDs), `manifest.json` (groups→sessions with transcript pointers), and `groups.json`
  (the DAG) into one payload the SPA can render.
- R4. Expose the run's event log (`logs/run.log`) as a live stream over **SSE**, tailing
  appended lines as the orchestrator writes them.
- R5. Push run changes: watch the run directory and emit lightweight "changed" events over
  SSE (debounced) so the SPA refetches the snapshot and pending-escalations list without
  fixed-interval polling for core state.
- R6. Expose pending escalations for a run (parse `escalations/request-*.json`, exclude any
  with a matching `response-*.json`), including correlation id, kind, and prompt text.
- R7. Expose a **write endpoint** to answer an escalation, taking correlation id, action
  (`answer` | `skip` | `abort`), and optional text, implemented by calling the
  orchestrator's existing `answer` code path (which validates and writes
  `response-<id>.json`). Reject stale/already-answered escalations.
- R8. Expose a per-session **transcript endpoint** that resolves the session's
  `transcript_path` from `manifest.json`, parses the `.jsonl`, and returns a normalized
  event list (tolerant of unknown event types), returning latest content on each call so
  the SPA can re-poll.
- R9. Serve finished and crashed runs from disk identically to live ones (post-mortem view)
  — nothing in the read path may assume a run is still active.
- R10. Make no changes to orchestrator execution/scheduler/session code paths; the server
  is strictly a reader plus the R7 answer write.

### Front-end (SPA)

- R11. Reuse the existing `ui/` React + Vite + TS prototype as the base, replacing its
  hardcoded fixtures (`sample-run.ts`) with a data layer that calls the backend.
- R12. Provide a **project switcher** (from R2) and, within a project, a **run switcher**
  (from R3).
- R13. Render the **group board** from the snapshot: one card per group showing its state,
  generation, and dependency edges (the DAG from `groups.json`).
- R14. Render the **event log** live from the R4 SSE stream.
- R15. Render **pending escalations** with an inline **answer form** (answer / skip /
  abort + text) that calls R7 and reflects the result once the run's next change arrives.
- R16. Provide a **transcript drill-in**: clicking a group opens a pane that loads its
  agent transcript via R8 and auto-refreshes every few seconds while open, rendering
  tool-calls, tool-results, and assistant messages.
- R17. Surface each group's finished **report/verdict** JSON (`groups/<gid>/*.json`) in the
  drill-in for completed rounds.

### Success criteria

- R18. End-to-end HITL loop, live: start a real (non-stubbed) `run --hitl` on a registered
  project, watch it in the Observatory, answer an escalation **from the UI**, and observe
  the run resume — the exact flow the live smoke run never exercised.
- R19. Cross-project: with two repos in the registry, switch between them and view each
  one's runs without restarting the server.
- R20. Post-mortem: open a completed or crashed run and read its board, log, DAG,
  escalations, and per-agent transcripts entirely from disk.

## Non-Goals

- Launching, resuming, or aborting runs, or managing groups, from the UI. **Explicitly a
  planned future improvement** — v1 stays observe + answer.
- Modifying the orchestrator to stream subagent output (`stream-json`) or otherwise
  changing its execution model.
- Editing plans, `groups.json`, or config from the UI.
- Authentication, multi-user, remote/hosted deployment, or TLS.
- Token-by-token real-time transcript streaming (true per-transcript SSE tail).
- Design polish beyond making the prototype legible (theming, mobile/responsive, etc.).

## Open Questions

- Web framework: Starlette (closest to what `fastmcp` already vendors) vs FastAPI (typed
  endpoints, small extra dep). Decide at plan time.
- Project Registry location: a global `~/.orchestrator-ui.yaml` vs a per-repo file vs a
  `--registry PATH` flag (or a combination). Lean global default; confirm at plan time.
- SPA delivery: `vite dev` alongside the backend in development vs the backend serving the
  built static assets for a single-command run. Lean toward both (dev split, shipped
  bundled); confirm at plan time.
